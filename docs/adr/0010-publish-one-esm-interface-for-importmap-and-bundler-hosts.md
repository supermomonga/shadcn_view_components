# Publish one ESM interface for importmap and bundler hosts

## Context and Problem Statement

Interactive components must work in Rails applications using import maps and in applications using a JavaScript bundler. Maintaining separate public module paths or compiled variants would make controller registration and internal imports diverge.

## Decision Drivers

* Keep a single public JavaScript module specifier.
* Support buildless importmap hosts and bundler hosts.
* Ship readable ESM without requiring a gem-side compilation step.
* Make installation idempotent and explicit.

## Considered Options

* Support import maps only.
* Publish a separate npm package for bundler hosts.
* Ship one ESM package in the gem and expose it through host-specific installation adapters.

## Decision Outcome

Chosen option: "Ship one ESM package in the gem and expose it through host-specific installation adapters". Both host types import `@supermomonga/shadcn-view-components`. The engine adds the importmap definition when import maps are available. The installer synchronizes the same ESM tree into a vendored local package for bundlers. Consumers explicitly call the shared `register(application)` entry point.

### Consequences

* Good, because source modules and internal specifiers are identical in both host types.
* Good, because importmap hosts remain buildless.
* Good, because bundler tests exercise the same package interface.
* Bad, because bundler hosts receive a synchronized copy that must be regenerated by the installer.
* Bad, because both adapter paths require consumer-level verification.

### Confirmation

Importmap integration tests, installer tests, JavaScript consumer tests, and package export coverage verify that every public controller and helper resolves through the shared specifier.
